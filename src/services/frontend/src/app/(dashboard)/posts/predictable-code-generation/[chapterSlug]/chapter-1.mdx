# Introduction

Many programmers are negative about the impact of code generation on code quality and on their profession in
general. I believe most of those people try to integrate code-generation into old workflows, which forces the
AI to guess about how it can best serve you, but results in surprising and sub-optimal decisions. To use
code-generation successfully, we have to rethink our workflows.

Below I will briefly go into the critical elements that determine code-generation outcomes. Next, I will
describe how we can design our AI-enabled workflow to produce better results. Finally, I will reference some
resources (that I created) which will help you to put this approach into practice. By adopting the TDD process
that is described below, you will probably see improvements quickly, but I expect that a few weeks of
experimentation are needed to create the full setup and workflow that suits your personal preferences.

# Success factors for code-generation

## Clear high-level specs encoded as tests

It’s essential that we communicate our requirements to the AI. The best way is to combine high-level scenarios
(you can leave out edge-cases or details, and just present the big picture of how the software achieves
different goals) with automated tests that serve as verifiable specs. These tests will be used in a TDD
approach in which all tests are written before the application code is generated.

## Optimized composable solutions to sub-problems

You also need to help the AI to cleanly compose your basic building blocks. Most code-bases are a complex sum
of simple solutions. These simple solutions are usually familiar territory (submit a form, process an api
request, etc) but the challenge is in combining them cleanly. When solutions are well-designed and composable,
then it’s relatively easy to build bigger systems out of them.

Therefore, we need to tell the AI what our favourite solutions are and make sure that the AI understands them
really well (by showing instructions and example code). When our application requirements map cleanly onto
known composable solutions, then AI will produce exactly what we expect to see.

Our composable solutions should rely mostly on functions. Class methods that do real work tie data and logic
together in a way that makes it hard for AI to identify and maintain the separation of concerns. I do like
OOP, it can be great, but I advise to use classes (when you need them) as glue code that delegate to functions
to do the heavy lifting.

## Combining composable solutions with verifiable specs

The combination of verifiable specs with optimized composable solutions is a powerful one. It offers a high
degree of confidence in _what_ the application will do (this is both instructed and verified by the tests) and
_how_ the application will do it (this is instructed by the known solutions that the requirements are mapped
onto).

# A process for creating scenarios and workflow-tests

Below, I will explain my process for creating scenarios and workflow-tests, and provide examples. The steps in
the process lead to a spec (that includes automated tests) that allows the AI to produce high quality code.

## The (throw-away) design document

The [design document](https://www.example.com/) is a temporary document that contains a brain-dump of our
ideas for new features. I prefer to organize it in milestones that each describe a workflow in which a user
(or application sub-system) achieves a goal, e.g. “a user authenticates with the backend console”. The
milestone describes both the typical use-case and edge-cases.

An important element of the design document is a glossary that briefly describes the main concepts. This lays
the conceptual groundwork for the application code, and it allows the milestones to be brief and dry.
Especially in the initial stages of the code-base, the usefulness of a glossary cannot be overstated, don’t
skip it!

When you are done with the design document then you should ask your AI to review it. I always use the phrase
“don’t focus too much on details, but catch weaknesses and gaps in the main features and workflows”.

## The (throw-away) test plan

When the design document is ready, ask your AI to translate it into a [test plan](https://www.example.com/)
that describes how the features will be tested. The AI is instructed to divide the test plan into batches. For
each batch it should tell you what will be tested, and which application code units will be exercised by these
tests.

Asking about the code units allows you to get a rough idea of the implementation direction. E.g. if the test
plan mentions the add_job_to_queue function, then you already know that the AI will introduce a job queue. In
my experience these implementation choices are usually correct (they are logical consequences of the design
doc), but it’s still important to know about them early on so that you can steer the AI in the right
direction.

The test-plan can propose both regular tests (in /tests) and e2e-tests (in /e2e_tests). The e2e_tests can
either use fakes at the boundaries (e.g. a fake git, docker compose, etc) or test against the real
dependencies.

## AI-generating workflow-tests

### What is a workflow-test?

I use the term [workflow-test](http://www.example.com) for an automated test that simulates a particular path
through the application code, e.g. a_user_logs_in_and_is_authenticated. This test is powered by a TestEnv
class that is a custom fixture that is tailor-made to execute a particular workflow. The test _never calls the
application code directly_, it only calls the test-env.

In turn, the test-env calls the application code and stores the results. Finally, the workflow test makes
assertions on the contents of the test-env.

### The test-env makes workflow-tests read like a script

Workflow-tests are highly readable because they call TestEnv methods that read like the elements of a script.
E.g. the workflow-test may call `env.create_a_session_in_which_the_user_is_not_registered()` followed by
`env.try_to_log_in_the_user()`. Then, the workflow-test may assert that `env.logged_in_users == [ ]`. If the
developer wants to understand how the application code is called, then they can jump into the functions of the
TestEnv class.

### Organization of the test files

I divide my workflow-tests into “regular” and “impl” categories, and tell the AI to put tests for details and
edge-cases into the “impl” directory. This way, a user who wants to get a basic understanding of the system
can focus on the regular tests and skip the impl tests.

Note that AI is incredibly good at writing workflow-tests. I won’t try to explain, just try it out. The
tendency of AI to write lots and lots of tests works in our favour, as long as we tell the AI to put every
test in its own file. A workflow-test usually tests several things within the same test-function, so that the
number of test files stays reasonable. Moreover, since the test filename tells us roughly what is tested, it’s
easy to navigate them.

### Testing frontend applications

You can write workflow-tests for the frontend (I use React) using Playwright. AI does a great job there too.

## AI-generating the code

Next, we ask the AI to split the tests in batches, enable these batches one by one, and generate the code so
that it passes the tests for that batch. The AI will base the code on the building blocks - and their related
instructions - that are contained in the composable solutions.

Among these instructions, the most important one is to create (what I call) focussed feature-packages that
contain focussed files. A feature-package encapsulates one particular functionality or concept of the
code-base, such as “hotel_rooms” or “bookings”. When you read out the list of feature-packages, then it should
sound like a high-level description of your application. Within a feature-package, the code is split into
models (plain data-structures, almost no logic), actions (functions that change the application state), rules
(functions that query the application state), utils, and a few other (optional) categories. By insisting that
the code is split up in this way, we counter the tendency of the AI agent to keep adding more features to the
same files (which leads to slop code).

## AI-refactoring the code (optional)

In my experience, the AI agent does a great job at creating focussed feature-packages and files, but it will
sometimes create a large action file that does the work of an entire feature-package. When this happens, it’s
because a feature-package was missing. I identify these cases by listing the n biggest python files in the
code base, and ask the agent to split up the big file by introducing a new feature-package (with a name
suggested by me).

## AI-generating high-level scenarios

At this point, our application requirements are encoded in the test-suite, but it would still be nice to have
a user-friendly high-level description of the features. Neither the design doc nor the workflow-tests serve
that purpose very well. Therefore, I ask my AI to create [scenario documents](http://www.example.com) (that
follow a known template) that explain the main features and workflows, while leaving out the edge-cases and
details (an interested user can consult the workflow-tests for those). As the scenarios are created, the
related parts are deleted from the design doc (until eventually the design doc is empty).

For capturing scenarios I use a special tool called [sunya](http://www.example.com), but you can of course
create your own format. My scenarios start with a `run_scenario` function that explains a workflow by walking
through pseudo-code. Next, there is a Markdown description of the scenario steps, followed by a sequence
diagram. All these three components overlap, but they also complement each other in nice ways.

Once the scenarios are generated, we can delete the design doc (which should be empty) and test plan.

## Updating the code-base using fast-tracking

If the requirements change, then we repeat the entire process. We ask the AI to write and/or update
workflow-tests, to update the scenarios, and finally to update the code so that all tests are green again.
When an update is easy (it fits perfectly in the existing structure) you can ask the agent to fast-track the
changes, which means that you review all the work (the design, the tests and the code) afterwards. This speeds
up the process.

# Resources to get you started

[mn-prompts](http://www.example.com): a repo with prompts and example code that explains to AI how to apply my
favourite composable solutions. It includes instructions on creating focussed feature-packages and files. You
can adapt this resource so that it uses your own favourite solutions and patterns.

# Conclusion

I’m excited that AI code generation will take care of most problems that have been troubling software
development. We will have fewer bugs, security issues, and code smells. Our attention will shift to
formulating our requirements and (for now, though maybe not too much longer) to the high-level architectural
ideas that will support the implementation of those requirements. Sadly, the art of tackling _implementation_
challenges will become a thing of the past, but as problem solvers, I’m sure we will find other types of
problems to work on.
